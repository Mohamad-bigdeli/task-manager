# Task Manager data and migrations

## Storage ownership

Use UUID identifiers generated by the owning service and UTC timestamps. Foreign service IDs are references, not cross-database foreign keys. Every query for tenant data binds workspace/project scope server-side. Database constraints complement application validation.

| Owner | Logical records and constraints |
| --- | --- |
| Identity PostgreSQL | `accounts`: unique normalized email, display name, timezone, active flag; `credentials`: password hash; `sessions`: refresh-token hash, token family, expiry/revocation; signing-key metadata references secret material |
| Workspace PostgreSQL | `workspaces`: kind, owner, state; `memberships`: unique workspace/user, role, state; `invitations`: email, token hash, role, expiry, consumed/revoked state; identity projection for invitation notification routing |
| Task PostgreSQL | `projects`: workspace, creator, visibility, archive state; `project_members`: unique project/user; `tasks`: project, assignee, status, priority, due time, version, assignment version, due version, deletion marker; append-only change history |
| Notifications PostgreSQL | `notifications`: recipient, type, source event, read timestamp; `reminders`: task/due version/recipient/due time/state; delivery attempts and scheduler claims |
| Search PostgreSQL | Disposable `search_documents`: resource ID/type, workspace/project IDs, source version, text-search vector, deletion marker; indexing cursors |
| AI PostgreSQL | Run ownership/status, approval/execution ledger, durable ingestion ledger, document lifecycle/tombstones, LangGraph checkpoint persistence through its supported adapter |
| AI MongoDB | Conversation messages, document descriptive metadata and extracted text, user-approved long-term memory; index by owner/workspace/project and lifecycle version |
| AI Qdrant | Derived chunks, embeddings, source IDs/versions, embedding model version, workspace/project filters; no authority to grant access |

One local PostgreSQL instance contains six databases with six application credentials. Each migrator uses its own elevated credential. MongoDB and Qdrant belong only to AI; Redis keys and credentials are namespaced by purpose/service. A separate Redis process serves Celery so cache eviction cannot discard queued work.

## Domain integrity

- A partial unique constraint permits one personal workspace per owner. Account-created redelivery performs an idempotent insert.
- Workspace ownership transfer updates the owner reference and both membership roles in one transaction under a workspace lock. Removing the owner is rejected.
- Invitations store a hash of a random bearer token. Acceptance locks the invitation, checks current email, expiry, workspace state, and membership, then consumes it and creates membership atomically. Repeated acceptance by the same account returns the existing outcome.
- Project ACL rows require an active member at mutation time through Workspace. Since this is a remote check, later access always revalidates membership too.
- Every task update increments a version and writes audit/outbox records in the same transaction. Updates use a version predicate; zero affected rows means a conflict or inaccessible/deleted resource, distinguished only after authorization.
- `assignment_version` increments only when the assignee changes; initial assignment counts as a change. `due_version` increments when due time, assignee, completion eligibility, or deletion changes. Reminder eligibility compares this generation, not the general task version, so editing a title cannot send another assignment or due notification. Reopening a past-due task creates a new eligible reminder generation.
- Project archive is a state change rather than physical deletion. Workspace archive blocks new writes and invitations; historical data remains readable to authorized members. Account erasure is an explicit later retention workflow, not an accidental cascade.

## Transactional support tables

Each PostgreSQL service that publishes or consumes events has an outbox and/or inbox. Outbox includes event ID, aggregate ID/version, subject, payload schema version, payload, creation time, publication status, attempts, and next-attempt time. Inbox has a unique `(consumer_name, event_id)` key and completion time.

Relays claim rows with bounded leases or row locking and publish outside long-running business transactions. Consumers transact deduplication and database effects together. Acknowledgment occurs after commit. External side effects use a separate durable delivery/execution ledger and an idempotency key at the remote owner; a local inbox transaction alone cannot make a remote call atomic.

HTTP mutation deduplication stores actor, route, workspace scope, key, normalized request hash, state, result status/body, and expiry. Initial retention is 24 hours; authorization is checked before returning a replay. A key reused with different input returns `409`. A concurrent unfinished request returns `409` with a retry hint. The mutation and completed result commit atomically where they share a database.

## Index and pool design

Start with indexes supporting actual queries: tasks by project/status and stable `(created_at, id)` cursor, assignee, due time; memberships by workspace/user; notifications by recipient and creation time; outbox by unpublished/next attempt. Index foreign-key columns used in local joins. Capture query plans before adding broader or duplicate indexes.

For local Go APIs, start with at most five open PostgreSQL connections per process and two idle connections. Workers and relays also have explicit bounded pools. Calculate the total across replicas and reserve capacity for migrations and administration before changing limits. Python API, Celery workers, and checkpoint adapters share a service connection budget, not one unrestricted pool per job. Pool acquisition obeys request deadlines.

## AI lifecycle across stores

Create an ingestion ledger record in PostgreSQL before dispatch. The job tracks source version, file location, extraction, MongoDB materialization, embedding, indexing, and completion. Workers use deterministic chunk IDs and upserts so restart does not duplicate chunks. Publish readiness only after all required stages succeed. A reconciliation task redispatches incomplete jobs and cleans orphaned staged files.

Document deletion first commits a tombstone in PostgreSQL. Retrieval checks that authoritative lifecycle state and current project permission before using content; MongoDB/Qdrant/file cleanup can follow asynchronously. A job must compare the current document generation before indexing or marking it ready, so an old ingestion attempt cannot resurrect a deletion. Embedding-model changes create a new index generation; do not mix vectors of incompatible dimensions.

Deleting conversation/memory marks it unavailable first and enqueues cleanup. Keep only identifiers and outcome metadata needed for audit/idempotency; remove text from MongoDB, vectors, and files. Local backups follow a documented retention policy and are not silently treated as live indexes.

## Migration workflow

Use versioned SQL migrations with `golang-migrate` for owned application tables. AI checkpoint tables follow the pinned checkpoint adapter's migration mechanism, under the same deployment gate. MongoDB uses versioned, resumable application migration scripts; Qdrant schema/model changes use new collection generations and controlled cutover.

1. Create an additive migration and test it on an empty database and the preceding released schema with representative data.
2. Run a single migration job per owner before compatible application processes start. Application credentials cannot perform DDL; startup verifies schema compatibility rather than auto-migrating concurrently.
3. For incompatible changes, expand, deploy code supporting both forms, backfill in bounded batches, verify, switch readers/writers, and contract in a later change.
4. Back up before destructive changes and test restoration. Prefer forward repair over an untested destructive down migration. Never rewrite an applied migration.
5. Record database version, application version, migration duration, and backup reference. Do not run broad cross-service migrations as one transaction.

## Data retention defaults

Retain local inbox/outbox/idempotency records long enough for the configured replay horizon. The initial business-event stream horizon is seven days; retain consumer deduplication for at least eight days. An intentional older replay must use a controlled rebuild or business uniqueness constraints, not assume expired inbox rows still protect effects. Durable notification uniqueness keys outlive replay retention.

Soft-deleted task content is excluded from reads and projections immediately; keep tombstones/version records for replay correctness. Physical purge and backup erasure are hardening tasks in S09. Development reset commands must name the target databases/volumes and require explicit destructive intent.
